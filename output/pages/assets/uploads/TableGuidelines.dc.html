Using Tables on the Website
Rules for building tables that stay readable on mobile — where most of our traffic happens.
“
UX comes before content. If a table can't be read comfortably on a phone, it should not go on the page as-is — restructure it or use a different format.
01 · When to Use a Table
✓ Use a table for
  • Comparing 2–4 items across a small set of shared attributes
  • Structured numeric or reference data (fees, thresholds, dates)
  • Content readers scan, not read start‑to‑end
✕ Use prose, a list, or cards for
  • Explaining a process, step, or requirement in detail
  • Long-form descriptions, benefits, or country write-ups
  • Anything a single cell can't hold in one short line
02 · Hard Limits
3
Columns max (incl. label)
6
Rows before "show more"
1
Data point per cell
Header text ≤ 18 characters
Cell text ≤ 40 characters
These are ceilings, not targets — the shortest label that stays clear always wins. Every column beyond the first must justify itself on a 375px screen.

03 · If a Table Runs Too Big
Restructure it, in this order
1
Cut to the essential columns. Keep only what a reader decides with — usually 2, never more than 3. Move supporting detail into a second line inside the same cell.
2
Split one table into several. Group rows by category (e.g. by region, by programme type) under their own subheading instead of one long table with many rows.
3
Push the rest one click deeper. Remaining detail becomes an expandable row, a linked country/programme page, or an FAQ — not another column.
4
Last resort: stacked cards. If the data genuinely needs 5+ attributes per item, ask design/dev for the card layout below rather than shrinking a table to fit.

Needs Dev Input
If a dataset can't be trimmed to these limits, don't force it into a static table — flag it to dev/design for a responsive pattern: sticky first column with horizontal scroll, collapse to stacked cards below 480px, or a "show more" row toggle. These are engineering changes, not something copy alone can fix.
